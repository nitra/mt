# Виділення репозиторію задач на проект при переході на структуру org=проект

**Status:** Proposed
**Date:** 2026-08-25

## Context and Problem Statement

Репозиторії реорганізуються за проектами: проект = організація в термінах git-хостингу (напр. проект `maya` включатиме 11 репозиторіїв, переміщених у org `maya`). У поточній архітектурі (0.3.0-draft, [graph.md](../architecture/graph.md), [git.md](../architecture/git.md)) шар задач `metatask/` живе **всередині** кожного репозиторію, з яким працює. Питання: чи варто в рамках нової структури виділити в кожному проекті окремий репозиторій під задачі (напр. `metatask`), замість того, щоб `metatask/` лишався розподіленим по кожному з N репозиторіїв проекту.

Ключове архітектурне обмеження, яке визначає простір рішень: **fenced publish** ([git.md](../architecture/git.md)) — публікація результату вузла є одним атомарним multi-ref push у `origin`, що одночасно кладе код у `refs/heads/main`, звільняє claim-реф (`refs/metatask/claims/<node-hash>`) і run-реф (`refs/metatask/runs/<node-hash>/<token>`). Це працює тільки тоді, коли worktree вузла — той самий репозиторій, куди йде код. Git не підтримує атомарний push у два різні remote одночасно.

## Considered Options

- **Варіант 1 — розділення за типом вузла.** Проектний `metatask/` (в окремому metatask-репо) тримає лише composite/організаційний шар декомпозиції. Атомарні листові вузли, що продукують код конкретного репо, фізично лишаються у `metatask/` того репо — fenced publish для них не змінюється. Metatask-репо посилається на них через crossrepo `ref:`.
- **Варіант 2 — two-phase publish з ідемпотентністю.** Публікація в два кроки: спочатку код у code-репо (commit trailer `Metatask-Node`/`Metatask-Run` для дедуплікації), потім окремим пушем — звільнення claim + `fact_NNN.md` у metatask-репо. Reconciliation-on-takeover закриває вікно між кроками.
- **Варіант 3 — git submodules/subtree.** Metatask-репо тримає code-репо як submodule; публікація = коміт у submodule → коміт у супер-проекті. Той самий порядок «код спочатку», що й варіант 2, але git-нативний запис відповідності код-коміт↔задача.
- **Варіант 4 — metatask-репо як агрегатор/дашборд.** `metatask/` для код-вузлів лишається де є зараз (усередині code-репо); metatask-репо — read-only проекція стану (аналог запланованого `metatask-dashboard`, roadmap M3). Не дає єдиного крос-репо графа для виконання, лише для огляду.
- **Варіант 5 — зовнішній координатор (2PC/saga через relay).** Відкинуто: відтворює atomic-push гарантію зі слабшими властивостями і додає нову точку відмови; складність не пропорційна виграшу порівняно з 1/4.

## Decision Outcome

Chosen option: **Варіант 1 (розділення за типом вузла)** як цільовий напрямок, з **Варіантом 4** як безризиковим проміжним кроком, якщо команда не готова одразу розширювати протокол `ref:`-посилань.

Обґрунтування:

1. Спостереження з [graph.md](../architecture/graph.md): composite-вузол (батько, що агрегує дітей) **не пише код** — по resolved усіх дітей wrapper пише лише синтетичну пару `run_NNN`/`fact_NNN` (actor: wrapper). Атомарність «код + звільнення claim» потрібна лише атомарним листовим вузлам, що реально виконують роботу в конкретному репо — проблема вужча за «весь граф».
2. Модель доступу вже узгоджена з цим напрямком: [access.md](../architecture/access.md) мапить `tasks(root_node_hash, owner_account, project_name, remote_url, …)` (назва таблиці — з періоду до doctrine-ADR; чи перейменовувати на `metatasks` разом з рештою — окремо не вирішено, поза скоупом цього ADR) — один root-node на один remote. Metatask-репо на проект = природний root-node для composite-шару всього проекту, а не для N окремих root-node.
3. Варіанти 2 і 3 залишаються як запасні техніки — на випадок, коли конкретний клас задач вимагає, щоб і композитний, і атомарний шар жили в одному metatask-репо (напр. дрібні crossrepo-скрипти без окремого «власного» code-репо).

### Синтаксис crossrepo `ref:`

```
<host>[:<port>]/<path-to-repo>@<path-in-metatask-tree>[#anchor]
```

Приклади:

```
ref: github.com/nitra/maya-api@metatask/task-x/fact_001.md#summary
ref: gitea.internal:3000/nitra/maya-api@metatask/task-x/fact_001.md
ref: gitlab.internal/nitra/platform/maya-api@metatask/task-x/fact_001.md   # GitLab-підгрупа, довільна глибина
```

- `<host>[:<port>]/<path-to-repo>` — URL-шлях без схеми (досить приліпити `https://` спереду для стандартного URL-парсера); `<path-to-repo>` — довільна кількість `/`-сегментів (GitLab-підгрупи, вкладені namespace в Gitea — обидва допущені [operations.md](../architecture/operations.md)), термінатор — сам `@`, не рахунок слешів.
- Двокрапка — виключно для порту.
- `@` — рівно один семантичний шов між «який репозиторій» і «який шлях у його `metatask/`-дереві»; не список токенів. Обрано замість початкового `;`: `@` не зливається візуально ні з чим іншим у рядку, на відміну від `;`, який на письмі важко відрізнити від `:`. Синхронізовано з ідентичним рішенням у графі онтології ([7n-ontology-mvp.md](https://git.7n.ai/ontology/doctrine), розділ «Ідентичність вузлів») — обидві системи адресують «репо + шлях усередині» одним і тим самим принципом і символом.
  - Колізія з git SCP-синтаксисом (`git@host:path`), де `@` розділяє user і host: у нашій позиції `@` стоїть між `<path-to-repo>` і `<path-in-metatask-tree>`, тобто вже за межами `<host>[:<port>]/<path-to-repo>` — парситься однозначно, збігу немає. Залишковий нюанс суто візуальний (звичка бачити `@` як «user@host»), не парсерний.
  - Перевірено на стандартному URL-парсері: у `https://github.com/nitra/maya-api@metatask/task-x/fact_001.md#summary` межу authority визначає перший `/` після `//` (тобто `github.com`), а `@` опиняється вже всередині path-компонента, де він — легальний нешифрований символ (RFC 3986, `pchar`) — жоден стандартний парсер не сприйме його як userinfo-роздільник.
- `#anchor` — без змін, перевикористовує наявну конвенцію (`…#section`, `… lines 5-20`, [graph.md](../architecture/graph.md)).
- Розрізнення з локальним `ref:`: наявність `@` — єдина ознака crossrepo-посилання; локальні відносні шляхи (`ref: ../collect-data/fact_001.md`) `@` не містять → чинна логіка резолюції не змінюється.

### Consequences

- Good, because зберігає інваріант fenced publish без змін для будь-якого вузла, що реально пише код — жодного нового класу race condition/merge-conflict.
- Good, because дозволяє єдиний крос-репо граф декомпозиції цілі проекту (зараз `deps/` резолвиться лише в межах одного `metatask/`-дерева) і единий membership/ролі на проект замість N окремих root-node.
- Good, because crossrepo-адреса URL-подібна й парситься стандартним URL-парсером після тривіального prefix-injection — не вимагає bespoke-парсера для кожного інструменту.
- Bad, because `deps/`-резолюція зараз навмисно не читає вміст файлів (`ls -R deps/` + strip `.md`, без читання вмісту) — crossrepo `ref:` цю економію ламає: оркестратору доведеться або ходити в чужий remote (`git ls-remote`/fetch чужих `refs/metatask/...`) при кожному scan, або тримати дзеркальний кеш стану інших репо в metatask-репо. Це окреме архітектурне рішення, не вирішене цим ADR.
- Bad, because git-креденшели виконавця (host role) тепер мають покривати і metatask-репо, і кожен потрібний code-репо — ACL-матриця зростає, а не спрощується ([access.md](../architecture/access.md)).
- Bad, because `mandates.md` оперує рівнями `blast_radius: node | subtree | repo | company` без рівня «проект з N репо» — задача, що зачіпає увесь проект, поки не мапиться чисто в жоден існуючий рівень; потребує окремого рішення при впровадженні мандатів на нову структуру.
